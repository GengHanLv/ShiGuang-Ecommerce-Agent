# 电商 Agent 项目面试准备

这是一份基于真实代码的复习提纲。没有任何网站能保证某题“必考”；这里把项目基础与公开面经反复涉及的方向标为优先准备。牛客面经属于用户自述，只作为问题线索，技术结论以源码和官方文档为准。检索日期为2026-10-18。

## 1 先准备两分钟项目介绍

“我做了一个电商客服Agent学习项目，前端使用Vue 3，后端使用FastAPI和LangGraph。请求进来后先加载会话，召回相关用户偏好，再通过规则优先、模型补全的方式识别多意图，并发查询订单和知识库，最后基于工具结果生成回答。订单事实来自MySQL；商品FAQ通过BGE-M3和Milvus检索；Redis保存最近历史和查询缓存。我重点关注用户隔离、稳定偏好更新、流式接口和失败兜底，并通过接口及规则回归检查。当前是本地演示系统，没有接入真实退款、人工客服或分布式事务。”

把“我重点关注”换成自己确实能讲清的工作。不要逐字背诵，更不要把AI协助生成的代码说成独立设计所有底层算法。

## 3 最高优先级 十五个问题

### 1 你的项目为什么算Agent 与聊天机器人有什么区别

回答：除模型生成外，还维护会话和偏好，根据意图执行订单查询和知识检索，使用工具事实形成回复。当前执行顺序由图固定控制，是工作流驱动的Agent。不是完全自主规划系统。

追问：为什么不用普通函数？当前可以用普通函数完成；图提供状态约定、节点组织和事件流，后续扩展路由更清晰。必须承认框架带来学习和依赖成本。

### 2 LangChain和LangGraph分别用了什么

回答：LangChain的消息对象与ChatOpenAI适配模型；LangGraph用StateGraph定义节点、边和状态合并。当前无checkpointer、条件边或ReAct循环。Redis保存历史和LangGraph持久化检查点是两回事。[官方Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)

### 3 State里的messages为什么会自动追加

回答：`Annotated[list[dict], operator.add]` 指定列表相加的reducer；节点返回一条新assistant消息会追加到输入历史。其他字段没有reducer则覆盖。若生成节点把旧历史再返回一次，会产生重复消息。

### 4 意图识别为什么规则优先

回答：明显的查单、政策问答和转人工可走稳定规则，减少不必要模型调用；歧义输入才模型补全，再做白名单和业务门控。限制是规则覆盖不足和误判，需要用多标签数据集验证，不能只统计单意图准确率。

### 5 MySQL Redis Milvus为何同时使用

回答：MySQL处理精确结构化事实，Redis保存短期共享状态和缓存，Milvus搜索语义相似资料与偏好。它们的查询模式和一致性目标不同。不能用向量相似度判断谁拥有订单，也不能把Redis过期历史当永久档案。

### 6 短期和长期记忆区别是什么

回答：短期是最近20条消息、1小时TTL；长期是跨会话稳定偏好与反馈，按user_id存Milvus。订单状态不保存为长期事实，新偏好先清洗再更新同主题旧内容。

追问：删除旧值后写新值失败怎么办？当前存在丢失窗口；改进可采用主题唯一标识、版本、软删除和可恢复流程。不要说已做强事务。

### 7 如何保证不会查到其他用户的订单或记忆

回答：订单SQL带 `WHERE user_id=:uid` 并绑定参数；记忆在Milvus请求里带用户过滤；Redis键包含用户和会话。过滤错误不应降级成全库查。现在user_id仍由客户端提供，因此共享API Key只适合演示；公网需从可信认证上下文取得身份。

### 8 RAG完整链路是什么

回答：解析→字符分块→Embedding→向量入库；查询→Embedding→候选召回→关键词重排→上下文→生成。这里500字符、约50字符重叠，不是500token，不支持OCR。换Embedding模型要重新匹配维度和向量空间。[BGE-M3模型说明](https://huggingface.co/BAAI/bge-m3)

### 9 项目混合检索到底怎么做

回答：名称叫hybrid_search，但实现只有稠密召回后的关键词加分，没有独立BM25通道。关键词补分不能召回候选集合外的结果。若要做真正多路召回，应分别取候选，再通过RRF等方法融合并评测。

追问：RRF是什么？是按各检索列表的名次贡献 `1/(k+rank)` 再求和，减弱不同原始分数尺度差异。这里k是平滑常数，不是Top-K。它是可研究的改进，当前代码未实现。

### 10 余弦相似度和重排分数能混用吗

回答：不应把它们解释成同一种置信度。当前关键词每次加0.3，排序分数可超过1，下游阈值有校准风险。改进可保留dense_score与rank_score两个字段，用标注数据选择过滤策略，避免关键词命中让低相关文本通过。

### 11 缓存怎么失效

回答：缓存键包含集合版本、Top-K、阈值和问题哈希；入库成功增加集合版本，新请求不会命中旧版本。旧键靠TTL过期。版本失效降低手动删除复杂度，但不意味着数据库和缓存修改是一个事务。

### 12 async/await会让模型推理并行加速吗

回答：异步主要避免等待I/O时阻塞其他请求；同步客户端和本地向量化放到to_thread。gather并发独立工具，但推理仍争用同一CPU/GPU，线程池和连接池也有限制，不能把异步当作无限并行。[FastAPI并发说明](https://fastapi.tiangolo.com/async/)

### 13 流式回答如何保证前端拿到完整结果

回答：后端只转发response标签的token，最后done事件带完整reply和session_id；前端增量显示但以done权威文本收尾。HTTP读取块不等于SSE事件边界，解析要缓冲拆帧。失败发error，前端应明确未完成，不能把部分token伪装成成功。

### 14 你做了哪些测试 可以证明什么

回答：公开版接口回归覆盖鉴权、请求校验、会话ID一致性、SSE不暴露分类内容、失败标记、隔离、上传清理和缓存版本；另有37条纯规则回归，前端有流解析测试。这些不证明真实LLM回答准确率，也不证明生产性能。检索和端到端还要独立标注集及真实模型评测。

### 15 你遇到的主要工程问题是什么

选能复现的一项：偏好陈述误判查单、旧记忆污染回答、SSE误转发内部分类结果、入库后仍读旧缓存或同会话并发覆盖。回答结构为“触发输入→错误影响→定位函数→修改→回归→剩余限制”。不要只说“优化了Prompt”。

## 4 进一步追问与答案要点

| 问题 | 回答要点 | 当前实现与可改进处 |
| --- | --- | --- |
| 缓存穿透 雪崩 击穿是什么 | 不存在的查询、集中失效、热点并发miss | 本项目有空结果缓存；没有完整single-flight、随机TTL或限流 |
| Redis宕机和恢复怎么办 | 有界本地兜底、过期、可观测与一致性 | 恢复后可能有旧值，多进程兜底不共享 |
| 会话锁是分布式的吗 | asyncio.Lock仅约束本进程事件循环 | 多worker需要会话排队、CAS或分布式锁 |
| SQL注入如何防 | 绑定参数而非字符串拼接；最小权限 | user_id是数据过滤，不能代替身份认证 |
| Milvus索引怎么选 | 召回、延迟、内存之间权衡；用精确基线比较 | 当前IVF_FLAT并非经过业务压测的最优选择 |
| Top-K和阈值怎么定 | 用标注问题评Recall@K、MRR、上下文噪声 | 不能直接把0.5当成50%概率 |
| 为什么需要reranker | 更精细判断query与文档关系，代价更高 | 当前无Cross-Encoder，不可写在已实现亮点里 |
| 如何减少幻觉 | 工具事实、资料来源、未知拒答、约束和评测 | Prompt不是绝对保证，需检查引用支撑 |
| 文档提示注入怎么办 | 来源信任、数据与指令隔离、工具权限限制 | 现有文本拼接仍有风险，无完整防御系统 |
| 如何接真实退款工具 | 鉴权、用户确认、幂等键、状态机、审计与补偿 | 当前没有写订单/支付能力 |
| Embedding本地和云端如何取舍 | 隐私、部署成本、延迟、吞吐及维护 | 本地BGE并不等于所有数据都不出网，聊天上下文仍发模型服务 |
| 多Agent有什么代价 | 额外调用、通信、冲突和评估复杂度 | 当前一套明确流程通常更易验证，无多Agent协商 |
| 用户点停止还会扣模型费用吗 | 客户端断开不保证远端取消 | 需供应商机制、取消传播与调用追踪 |
| 上传失败是否回滚 | 分批写入可能残留，需文档ID和状态管理 | 当前上传不是事务；演示seed仅按正文增量去重 |
| 线上怎么观测 | 请求ID、节点耗时、工具错误、token成本、分位延迟 | 当前基础日志，无完整tracing与监控平台 |

## 5 评测应该怎样设计

先区分三层：意图分类是否正确、检索是否找到证据、最终回复是否忠于证据。不要只用另一个LLM给一个总分。

- 意图层：人工标注单意图、多意图、口语、歧义和无关输入；多标签可看exact match、micro/macro F1及误转人工率。
- 检索层：每问题标注可接受文档ID，计算Recall@3/5、MRR，记录无答案问题的误召回。用固定测试集比较分块、Top-K、索引和重排。
- 回答层：检查事实正确、是否引用支持、是否编造功能或真实业务操作、未知能否明确说明。另统计任务完成率、首token延迟、完整回复延迟、失败率和单次成本。

例如20个有答案测试问题中16个在Top-3找到正确证据，才可在这个测试集上报告80%的命中率；不要把这个教学示例数字写成项目实测。训练/调参集与最终评测集应分开，避免反复调同10个问题后宣称泛化。

公开样例只有12条虚构知识，适合验证能否跑通，不足以证明真实平台客服质量。私人数据的测试结果不应冒充公开仓库可复现成绩。

## 7 一次模拟面试的自查清单

1. 不看图说清“订单1怎么退”经过的函数与两个数据源。
2. 展示一个确实运行通过的测试，解释mock掉了什么、没有证明什么。
3. 现场指出用户隔离在SQL、Milvus和Redis分别哪一层完成。
4. 解释为什么检索分数可以大于1，并提出可验证的修正计划。
5. 说明将单worker改成4个后，会话锁与模型内存会有什么问题。
6. 明确自己没有实现的部分：真实人工客服、BM25、RRF、Cross-Encoder、ReAct、分布式事务及线上QPS指标。

## 8 如何把项目写进简历

可以写：基于LangGraph拆分四个节点；结合规则和模型进行多意图识别；按用户隔离检索偏好；用Redis会话及缓存版本管理；实现JSON/SSE和知识上传；补充接口与规则回归。

只有自己能解释和复现的内容才留在简历。不要写“独立训练大模型”“实现完整支付退款”“支持上万QPS”“准确率提升90%”等未经项目证据支持的表述。若借助AI编码，面试可如实说明辅助方式，并展示自己理解、测试和验证的部分。
